# 对外传播

## 目标用户

### 采用者

- 正在建设 AI-native 工作方式的公司创始人、技术负责人和 AI 平台负责人。
- 已经使用 Git 管理规则、架构、流程、产品知识或 Agent 指令的团队。
- 希望知识可以被多种 Agent 和自动化直接使用，而不绑定单一文档平台的组织。

### 日常用户

- 需要阅读或维护公司知识，但不熟悉 Git 和 Markdown 的运营、产品、HR、销售和管理人员。
- 需要审阅 AI Agent 所产生文档改动的知识负责人。
- 希望使用更轻量界面的开发者和技术团队成员。

## 对外叙事

### 问题

AI-native 团队希望把公司知识放在 Agent 可以直接读取和修改的文件系统里，因此开始使用 Git 仓库；但 Git 仓库
只对开发者友好，普通员工很难参与维护。

### 解决方案

Git Leaf 在 Git 仓库前提供一个简单的桌面工作台，让所有员工可以像使用普通文档工具一样阅读、搜索、编辑和同步，
而 AI Agent 仍然直接使用原始文件。

### 核心文案

中文：

> 让 Git 仓库同时对人和 AI 友好。

英文：

> The human interface for your AI-native knowledge base.

推广不得把 Git Leaf 描述为 VS Code、Obsidian、飞书文档或 Google Docs 的全面替代品，也不得把最近完成的某一项
功能提升为整个产品定义。所有对外主张都必须能够由当前产品、公开代码、测试、截图或可重复演示直接证明。

## 演示主线

首要演示应覆盖完整的人机知识循环，而不是孤立功能：

1. 打开一个示例公司知识仓库。
2. 像普通文档一样搜索、阅读和编辑。
3. 一步同步到 Git。
4. 让外部 AI Agent 直接读取更新后的规则并完成任务。
5. 让 Agent 更新相关文档。
6. 回到 Git Leaf 阅读和检查 Agent 的修改。

Agent 上下文可以作为后半段补充，用于展示 Agent 没有仓库访问权时的精确内容移交，但不应成为整段演示的唯一主角。

## 传播原则

- 从目标用户的工作问题出发，不从功能清单出发。
- 优先展示真实产品和完整工作流，不用概念图代替可试用结果。
- 针对不同渠道重新组织内容，避免原文批量复制到多个社区。
- 明确 Git Leaf 的适用边界，不制造“替代所有文档工具”的预期。
- 每项功能、数据和用户结论都关联可核验的证据。
- GitHub Stars、浏览量和点赞只作为渠道信号，最终关注真实安装、首次成功使用和持续使用。

## 开源方式

Git Leaf 使用经过脱敏的新公开仓库作为后续唯一产品源码。当前私有仓库包含不应公开的历史公司文档，完成迁移后只读
归档，不与公开仓库长期双向维护；内部员工也使用公开仓库产生的同一产品版本。

公司继续作为 Git Leaf 的维护者和官方发行者：

- 官方 macOS／Windows 安装包使用公司证书签名。
- 内部和外部用户从同一个官方入口下载，并通过现有官方更新服务自动更新。
- 公司维护者身份、签名证书中的公开身份、下载域名和更新地址不属于需要隐藏的信息。
- 证书私钥、发布凭据、服务器管理权限、内部文档、个人信息和不必要的基础设施细节不得进入公开仓库。
- 本地源码构建和第三方构建必须与公司签名的官方稳定构建明确区分，不能冒充官方发行版。

## 开源组织

Git Leaf 开源初期继续使用公司当前的 GitHub Organization，不为了品牌观感提前创建或迁移到新的产品
Organization。当前优先验证产品是否真的被需要、是否有人关注和是否有人愿意使用或参与。

只有项目形成真实的外部关注和持续参与，并且当前 Organization 名称开始妨碍产品认知或社区发展时，再评估迁移到
更友好的产品品牌 Organization。组织命名不是开源前置条件。

## 开源预期

Git Leaf 开源后不预设一定能够获得外部关注。即使暂时没有外部用户，公开源码仍然可以服务公司内部使用，并提供代码
透明和官方发行入口。
